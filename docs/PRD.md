## 1. 개요

FRMS는 IoT 플랫폼의 **기능 요구사항 한 건이 접수부터 완료까지 어느 단계에 있고 지금
누가 처리해야 하는지를 한 화면에서 보여주는** 웹 애플리케이션이다. 사업담당·개발담당·
UI담당·검수담당 4개 역할이 하나의 요구사항 원장(single source of truth)을 공유하고,
단계 전이는 역할별 권한과 필수 입력 규칙에 의해 강제된다. 특히 검수 단계의
**보완요청은 "어디로 되돌아가는가"(요건/UI/구현)를 반드시 분류**하게 하여, 반복되는
재작업의 원인이 데이터로 드러나게 한다.

최소 기능(MVP)으로 먼저 출시해 실사용으로 검증한 뒤, 각 단계의 종료 조건(Exit Criteria)을
충족했을 때만 다음 단계로 확장한다.

## 2. 배경 및 문제 정의

현재 IoT 플랫폼의 기능 요구사항은 MS Teams 채널 대화와 SharePoint 리스트, 개인 메일과
엑셀에 흩어져 관리된다. 그 결과 다음 문제가 반복된다.

| # | 문제 | 구체적 증상 |
|---|---|---|
| P1 | **진행 상태가 보이지 않는다** | "그 건 지금 어떻게 됐나요?"를 채널에 물어봐야 알 수 있다. 주간 회의 전에 담당자가 수작업으로 현황을 취합한다. |
| P2 | **책임 소재가 흐릿하다** | 요구사항이 접수됐지만 개발·UI·검수 중 누가 다음 행동을 해야 하는지 명시되지 않아, 아무도 손대지 않은 채 며칠이 흐른다. |
| P3 | **보완요청이 추적되지 않는다** | 검수에서 반려된 건이 채널 댓글로만 전달된다. 그것이 요건이 틀린 것인지, 화면 설계가 틀린 것인지, 구현 결함인지 구분되지 않고, 몇 번째 반려인지도 남지 않는다. |
| P4 | **요건이 조용히 바뀐다** | 개발 착수 후 사업담당이 SharePoint 항목을 직접 수정해도 개발담당이 인지하지 못한다. 변경 이력이 없어 나중에 책임 규명이 불가능하다. |
| P5 | **지표가 없다** | 요구사항 하나가 평균 며칠 걸리는지, 어느 단계에서 가장 오래 막히는지, 첫 검수 통과율이 얼마인지 아무도 답하지 못한다. 개선의 근거를 만들 수 없다. |

이 문제들의 공통 원인은 **요구사항에 상태(state)라는 개념이 없다는 것**이다. 리스트에
행이 하나 추가될 뿐 그것이 워크플로 위 어디에 있는지를 시스템이 알지 못한다.

## 3. 목표 / 비목표

### 3.1 목표

| # | 목표 | 검증 방법 |
|---|---|---|
| G1 | 모든 신규 기능 요구사항이 FRMS를 통해 접수·관리된다 | 신규 요구사항 중 시스템 경유 비율 100% |
| G2 | 요구사항의 현재 단계와 담당자를 클릭 없이 한 화면에서 파악한다 | 칸반 보드 1회 로드로 전 건 상태 확인. 사용성 테스트에서 "현재 상태 파악까지 5초 이내" 통과 |
| G3 | 각 역할이 로그인 직후 "지금 내가 해야 할 일"을 즉시 확인한다 | 내 할 일 큐에서 처리 대상 누락 0건 |
| G4 | 보완요청의 회귀 원인이 분류되어 집계된다 | 보완요청 100%가 회귀 대상(요건/UI/구현) 값을 보유 |
| G5 | 요구사항 처리 지표를 시스템이 자동 산출한다 | 리드타임·보완요청률·기한 준수율이 대시보드에서 조회 가능 (Phase 2) |

### 3.2 비목표 (Non-goals)

명시적으로 **하지 않는** 것들이다. 범위 확산을 막기 위해 문서에 못박는다.

| # | 비목표 | 이유 |
|---|---|---|
| N1 | **MVP에서 MS Teams 앱·봇·채널 알림 연동을 하지 않는다** | 두 플랫폼을 동시에 검증하면 MVP가 무거워진다. [결정 기록](./platform-decision.md) 참조. Phase 3 선택 과제로 유예 |
| N2 | 이슈 트래커(Jira/GitHub Issues)를 대체하지 않는다 | FRMS는 "요구사항"의 원장이지 개발 작업(task)의 원장이 아니다. 스프린트·브랜치·커밋 관리는 기존 도구가 담당 |
| N3 | 소스코드·빌드·배포 파이프라인과 연동하지 않는다 | Phase 3 이후 검토 |
| N4 | 프로젝트/포트폴리오 관리(간트, 자원 배분, 예산)를 하지 않는다 | 20명 규모에서 필요하지 않다 |
| N5 | 외부 협력사·고객이 직접 요구사항을 등록하는 포털을 제공하지 않는다 | 사내 인증(Entra ID) 기반으로만 운영. 외부 유입은 사업담당이 대리 등록 |
| N6 | 모바일 전용 앱을 만들지 않는다 | 반응형 웹으로 조회는 가능하게 하되, 네이티브 앱은 만들지 않는다 |

## 4. 대상 사용자 및 페르소나

총 사용자 약 20명. 한 사람이 여러 역할을 겸할 수 있다.

### 4.1 사업담당 (BIZ)

- **하는 일**: 고객·시장 요구를 수집해 기능 요구사항으로 정리하고, 우선순위와 희망 일정을 제시한다. 완료 후 실제로 원하던 것이 나왔는지 확인한다.
- **목표**: 내가 올린 요구사항이 지금 어디까지 갔는지, 언제쯤 나올지 알고 싶다.
- **불편**: 채널에 물어보지 않으면 진행 상황을 모른다. 요청한 것과 다르게 나와도 개발이 끝난 뒤에야 안다.
- **FRMS에서**: 요구사항을 등록·제출하고, 내 요청 현황을 추적하고, 결과가 다르면 보완요청을 올린다.

### 4.2 개발담당 (DEV)

- **하는 일**: 요구사항의 실현 가능성과 공수를 판단하고, 승인 후 구현한다.
- **목표**: 확정된 요건만 받고 싶다. 개발 중 요건이 바뀌면 명시적으로 알고 싶다.
- **불편**: 요건이 모호한 채로 넘어온다. 승인 후 사업담당이 리스트를 몰래 고친다. 검수 반려 사유가 구현 문제인지 요건 문제인지 불분명하다.
- **FRMS에서**: 요건검토에서 공수·목표일을 확정하고, 개발 완료를 선언하고, 구현 관련 보완요청을 접수한다.

### 4.3 UI담당 (UI)

- **하는 일**: 화면·플로우를 설계하고 산출물을 개발담당에게 전달한다.
- **목표**: 내가 설계해야 할 건이 무엇이고 언제까지인지 알고 싶다.
- **불편**: UI 변경이 필요한 건과 아닌 건이 섞여 들어온다. 설계 산출물이 어디 있는지 매번 찾아야 한다.
- **FRMS에서**: UI설계 단계 대상만 골라 보고, 산출물 링크를 FR에 첨부하고, UI 관련 보완요청을 접수한다.

### 4.4 검수담당 (QA)

- **하는 일**: 완료 조건에 따라 테스트하고 통과/보완요청을 판정한다.
- **목표**: 무엇을 기준으로 검수해야 하는지 명확했으면 좋겠다. 반려 사유가 제대로 전달됐으면 좋겠다.
- **불편**: 완료 조건이 없어 무엇을 확인해야 할지 모른다. 반려 내용이 채널 대화에 묻힌다. 같은 건을 몇 번째 반려하는지 기억에 의존한다.
- **FRMS에서**: 검수 대기 건을 큐로 받고, 완료 조건을 기준으로 판정하고, 보완요청 시 회귀 대상을 지정한다.

### 4.5 관리자 (ADMIN)

사용자·역할을 관리하고, 운영 사고 시 상태를 복구한다. 별도 인력이 아니라 개발담당 중
1명이 겸한다.

## 5. 핵심 유저 스토리

### 사업담당

- **US-B1** 사업담당으로서 새 기능 요구사항을 배경·상세내용·완료조건과 함께 등록하고 싶다. 그래야 구두 전달로 인한 누락 없이 요건이 남는다.
- **US-B2** 사업담당으로서 내가 올린 요구사항들의 현재 단계를 한 화면에서 보고 싶다. 그래야 매번 담당자에게 물어보지 않아도 된다.
- **US-B3** 사업담당으로서 완료된 결과가 요청과 다르면 무엇이 다른지 적어 되돌리고 싶다. 그래야 재작업 요청이 채널 대화에 묻히지 않는다.
- **US-B4** 사업담당으로서 우선순위가 밀린 요구사항을 보류로 옮겨두고 싶다. 그래야 진행 중 목록이 깨끗해진다.

### 개발담당

- **US-D1** 개발담당으로서 접수된 요구사항을 검토해 예상 공수와 목표 완료일을 확정하고 싶다. 그래야 일정 약속의 근거가 남는다.
- **US-D2** 개발담당으로서 UI 변경이 필요 없는 건은 UI설계 단계를 건너뛰고 바로 개발로 보내고 싶다. 그래야 불필요한 대기가 없다.
- **US-D3** 개발담당으로서 승인 이후에는 요건이 임의로 수정되지 않기를 바란다. 그래야 개발 중 요건이 흔들리지 않는다.
- **US-D4** 개발담당으로서 구현 문제로 분류된 보완요청만 내 큐에 들어오길 바란다. 그래야 요건 문제까지 내가 떠안지 않는다.

### UI담당

- **US-U1** UI담당으로서 UI설계가 필요한 건만 모아 보고 싶다. 그래야 내 작업 대상이 명확하다.
- **US-U2** UI담당으로서 설계 산출물 링크를 요구사항에 붙여 두고 싶다. 그래야 개발·검수담당이 매번 찾아 헤매지 않는다.
- **US-U3** UI담당으로서 UI 문제로 분류된 보완요청을 접수해 다시 설계 단계로 가져오고 싶다.

### 검수담당

- **US-Q1** 검수담당으로서 검수 대기 건과 그 완료 조건을 함께 보고 싶다. 그래야 무엇을 확인할지 판단할 수 있다.
- **US-Q2** 검수담당으로서 보완요청 시 요건/UI/구현 중 어디 문제인지 지정하고 싶다. 그래야 올바른 담당자에게 바로 넘어간다.
- **US-Q3** 검수담당으로서 이 건이 몇 번째 보완요청인지 보고 싶다. 그래야 반복 재작업을 근거와 함께 문제 제기할 수 있다.

### 공통

- **US-C1** 모든 사용자로서 사내 계정으로 별도 가입 없이 로그인하고 싶다.
- **US-C2** 모든 사용자로서 요구사항의 변경·전이 이력을 시간순으로 보고 싶다. 그래야 "왜 이렇게 됐는지"를 나중에 확인할 수 있다.

## 6. 기능 요구사항

**우선순위**: Must(필수) / Should(중요) / Could(선택)
**Phase**: 구현 대상 단계 — 상세는 [로드맵](./roadmap.md) 참조

### 6.1 요구사항 관리 (FR-1xx)

| ID | 요구사항 | 상세 | 우선순위 | Phase |
|---|---|---|---|---|
| FR-101 | 요구사항 등록 | 사업담당이 제목·배경·상세내용·대상제품·기능구분을 입력해 신규 FR을 생성한다. 생성 즉시 `DRAFT` 상태가 된다 | Must | 1 |
| FR-102 | 임시저장 | `DRAFT` 상태에서는 필수 항목이 비어 있어도 저장된다. 제출 시점에 완료조건·우선순위·희망완료일 필수 검증을 수행한다 | Must | 1 |
| FR-103 | 요구사항 수정 | 필드 그룹별로 편집 권한과 편집 가능 상태를 강제한다. [데이터 모델 6.2절](./data-model.md#62-필드-그룹별-편집-가능-상태) 기준 | Must | 1 |
| FR-104 | 목록 조회 및 필터 | 상태·우선순위·담당자·대상제품·기간으로 필터링. 기본값은 "종결되지 않은 전 건" | Must | 1 |
| FR-105 | 상세 조회 | 요건 정보, 계획 정보, 담당자, 진행 스테퍼, 보완요청 이력, 변경 이력을 한 페이지에 표시한다 | Must | 1 |
| FR-106 | 키워드 검색 | 제목·상세내용·FR 키에 대한 부분일치 검색 | Should | 2 |
| FR-107 | 저장 필터 | 자주 쓰는 필터 조합을 이름 붙여 저장하고 재사용한다 | Could | 2 |
| FR-108 | 취소 처리 | 요구사항은 물리 삭제하지 않고 `CANCELED` 상태로 종결한다. 취소 사유 필수 | Must | 1 |
| FR-109 | ID 자동 채번 | `FR-YYYY-NNNN` 형식으로 생성 시점에 부여하며 이후 변경·재사용하지 않는다 | Must | 1 |

### 6.2 진행단계 워크플로 (FR-2xx)

| ID | 요구사항 | 상세 | 우선순위 | Phase |
|---|---|---|---|---|
| FR-201 | 상태 전이 실행 | [전이 매트릭스](./data-model.md#5-상태-전이-매트릭스)에 정의된 전이만 수행 가능하다. 정의되지 않은 조합은 API에서 거부한다 | Must | 1 |
| FR-202 | 전이 권한 강제 | 각 전이는 허용 역할, 그리고 해당 FR에 **지정된 담당자 본인**인지까지 검증한다. 역할만 보유한 제3자는 전이할 수 없다 | Must | 1 |

## 7. 화면 및 UX 요구사항

이 절은 목표 G2("클릭 없이 한 화면에서 파악")를 구체적인 화면 규격으로 옮긴 것이다.

### 7.1 화면 구성

| 화면 | 경로 | 목적 | Phase |
|---|---|---|---|
| 칸반 보드 | `/board` | **랜딩 화면.** 전체 요구사항의 단계별 분포를 한눈에 | 1 |
| 내 할 일 | `/my-queue` | 로그인 사용자가 지금 처리 가능한 건만 | 1 |
| 목록 | `/list` | 정렬·다중 필터·대량 확인 | 1 |
| 상세 | `/fr/{fr_key}` | 단일 요구사항의 모든 정보와 행동 | 1 |
| 등록·수정 | `/fr/new`, `/fr/{fr_key}/edit` | 요구사항 입력 | 1 |
| 대시보드 | `/dashboard` | 지표와 병목 | 2 |
| 관리자 | `/admin/users` | 사용자·역할 관리 | 1 |

### 7.2 칸반 보드 (FR-501, FR-504)

- **컬럼**: `접수` · `요건검토` · `UI설계` · `개발중` · `개발완료` · `검수중` · `보완요청` · `완료`
  - `작성중`(DRAFT)은 작성자 본인에게만 별도 섹션으로 보인다. 남의 미완성 초안은 노이즈다.
  - `보류` · `반려` · `취소`는 기본 숨김이며 토글로 표시한다.
  - **`보완요청` 컬럼은 시각적으로 강조**한다(경고색 헤더). 여기 쌓인 카드가 곧 재작업 부채다.
- **카드에 표시할 것** — 이 6가지 외에는 넣지 않는다:
  1. FR 키 + 제목(2줄까지)
  2. 우선순위 뱃지 (`P0`~`P3`)
  3. 현재 공을 쥔 담당자 이름/이니셜
  4. 목표 완료일 D-day (`D-3`, `D+2`)
  5. 지연 표시 (`D+`인 경우)
  6. 보완요청 횟수 (`↺ 2` — 1회 이상일 때만)
- **컬럼 헤더**에 해당 상태의 건수와, 그중 지연 건수를 함께 표시한다.
- 카드 드래그로 상태를 바꾸지 **않는다**. 전이는 필수 입력값 검증이 필요하므로 상세 화면
  또는 전이 다이얼로그를 통해서만 수행한다. 드래그는 규칙을 우회하게 만든다.

### 7.3 진행 스테퍼 (FR-502)

상세 화면 최상단에 가로 스테퍼를 배치한다.

```
접수 ──▶ 요건검토 ──▶ UI설계 ──▶ 개발중 ──▶ 개발완료 ──▶ 검수중 ──▶ 완료
 ✓         ✓           ✓          ●                                        
                                  ↑ 보완요청 2회차 · 구현 회귀 (2026-08-20)
```

- 완료 단계는 체크 + 채워진 색, 현재 단계는 굵은 테두리 + 펄스, 미도달은 연한 회색.
- `ui_change_required=false`인 건은 `UI설계` 단계를 회색 점선으로 "생략됨" 표기한다.
- 보완요청으로 회귀한 이력이 있으면 회귀 지점에 마커를 찍고 회차·회귀 대상·일자를 표시한다.
- 스테퍼 바로 아래에 **현재 사용자가 수행 가능한 전이 버튼**만 배치한다 (FR-208).

### 7.4 내 할 일 큐 (FR-503)

- 판정 기준은 역할이 아니라 **"이 사용자가 지금 이 FR에서 수행 가능한 전이가 1개 이상 존재하는가"** 이다. 전이 매트릭스로부터 파생되므로 별도 규칙을 두지 않는다.
- **단, 취소·반려 같은 파괴적 전이는 판정에서 제외한다.** 취소(T22)는 사업담당이라면
  진행 중인 거의 모든 건에 대해 가능하므로, 그것까지 세면 사업담당의 큐가 "취소할 수
  있는 건 전부"가 되어 목적을 잃는다. 큐는 "내가 다음 행동을 해야 하는 것"이지
  "내가 손댈 수 있는 것"이 아니다. (버튼 자체는 상세 화면에 그대로 노출된다.)
- 정렬: 지연 건 → 우선순위 → 목표 완료일 순.
- 각 항목에 수행 가능한 전이를 즉시 실행 버튼으로 노출한다.
- 큐가 비면 "지금 처리할 항목이 없습니다"를 명시적으로 표시한다.

### 7.5 색상·뱃지 규칙 (FR-508)

| 의미 | 색 | 아이콘/텍스트 | 비고 |
|---|---|---|---|
| P0 긴급 | 적색 | `P0` + 느낌표 | 색만으로 구분 금지 |
| P1 높음 | 주황 | `P1` | |
| P2 보통 | 청색 | `P2` | |
| P3 낮음 | 회색 | `P3` | |
| 정상 진행 | 중립 | — | |
| 지연 | 적색 테두리 | `D+n` + 경고 아이콘 | |
| 보완요청 | 경고 황색 | `↺ n` | 컬럼 헤더도 동일 색 |
| 종결(완료) | 녹색 | 체크 | |
| 종결(반려·취소) | 회색 | 사선 처리 | |

- 모든 상태·우선순위·지연 표시는 **색 + 형태/텍스트 이중 인코딩**을 지킨다.
- 전경/배경 명도 대비는 WCAG 2.1 AA(본문 4.5:1, 큰 텍스트 3:1) 이상.
- 키보드만으로 보드 탐색과 전이 실행이 가능해야 한다.

### 7.6 공통 UX 원칙

- **불가능한 행동은 노출하지 않는다.** 권한 없는 전이 버튼은 비활성이 아니라 숨김.
- **필수 입력은 전이 시점에 받는다.** 승인하려는데 공수가 없다면, 그 자리에서 입력받는다. 별도 화면으로 보내지 않는다.
- **되돌릴 수 없는 행동은 확인받는다.** 취소·반려는 사유 입력을 겸한 확인 다이얼로그.
- 반응형: 데스크톱 우선, 태블릿·모바일에서는 **조회 가능** 수준을 보장한다(보드는 컬럼 가로 스크롤).

| 인증 | Microsoft Entra ID OIDC(Authorization Code + PKCE). 자체 비밀번호 저장 금지 |
| 인가 | 모든 쓰기·전이 API에서 서버 측 권한 검증. 프론트엔드의 UI 숨김은 편의일 뿐 보안 경계가 아니다 |
| 감사 | 전이·필드 변경 이력은 append-only. 애플리케이션 경로로 수정·삭제 불가 |
| 가용성 | 업무시간(평일 09~19시) 기준 99% 목표. 무중단 배포는 요구하지 않는다 |
| 백업 | DB 일 1회 전체 백업, 보관 30일. 분기 1회 복구 훈련 |
| 보안 | 전 구간 HTTPS. 첨부파일은 웹 루트 외부에 저장하고 인증된 요청에만 서빙. 업로드 파일 확장자·용량 화이트리스트 |
| 로깅 | 요청 로그와 애플리케이션 로그를 구조화(JSON)해 남긴다. 개인정보(이메일 전체)는 로그에 남기지 않는다 |
| 브라우저 | 최신 Chrome / Edge (최근 2개 버전). Internet Explorer 미지원 |
| 국제화 | 한국어 단일 언어. 문자열은 사전으로 분리하되 다국어 전환 기능은 만들지 않는다 |
| 시간대 | 저장은 UTC, 표시는 Asia/Seoul |

## 9. 기술 스택

> **Phase 1에서 확정·구현되었다.** 선택 기준은 "20명 규모에서 1명이 개발하고 유지보수할
> 수 있는가"였다. 실행 방법은 [README](../README.md#실행) 참조.

| 계층 | 채택 | 이유 |
|---|---|---|
| 언어 | **Python 3.11 이상** | 단일 언어로 유지보수 인원을 최소화. 하한은 `StrEnum`(3.11+)이 결정하며, `X \| None` 유니온 문법도 3.10+를 요구한다. 3.11 미만에서는 `app/__init__.py`의 버전 가드가 안내와 함께 즉시 중단시킨다 |
| 웹 | FastAPI + Jinja2 서버 사이드 렌더링 | 빌드 단계가 없고 자바스크립트 없이 전 기능이 동작한다. 뒤로가기·새로고침·링크 공유가 그대로 통한다 |
| 백엔드 | SQLAlchemy 2.0 | 전이 매트릭스를 선언적 자료구조로 표현하고, DB를 URL 하나로 교체 가능 |
| DB | SQLite (기본) / PostgreSQL (운영) | `DATABASE_URL` 만 바꾸면 전환된다. MVP 검증에는 설치가 필요 없는 SQLite로 충분 |
| 인증 | Entra ID OIDC (Authlib) + 개발용 로컬 로그인 | 사내 계정 그대로 사용. Entra 설정이 없으면 로컬 로그인으로 동작해 오픈 이슈 O3 해결 전에도 검증할 수 있다 |
| 배포 | 단일 프로세스 (uvicorn) | 20명 규모에 Kubernetes는 과잉. 호스팅 위치는 오픈 이슈 O1 |
| 테스트 | pytest (도메인 + HTTP 계층) | 전이 매트릭스 전건과 거부 시나리오를 검증하는 것이 이 제품의 핵심 테스트 |

**React + TypeScript 대신 서버 렌더링을 택한 이유**: 초안에서는 React SPA를 제안했으나,
칸반·스테퍼·큐는 상호작용이 거의 없는 읽기 위주 화면이라 SPA가 주는 이득이 작았다.
반면 빌드 파이프라인·타입 정의 이중화·상태 동기화라는 비용은 그대로 발생한다.
MVP 검증 속도를 우선해 서버 렌더링으로 확정했다. Phase 3에서 공개 API(FR-803)가
생기면 그때 프론트를 분리할 수 있다.

**마이그레이션**: MVP는 `create_all` 로 스키마를 만든다. Phase 2에서 스키마 변경이
시작되는 시점에 Alembic을 도입한다.

**설계 원칙**: 상태 전이 매트릭스를 **코드 안 단일 선언 테이블**로 두고, 권한 검증·필수
입력 검증·UI 버튼 노출·내 할 일 큐를 모두 그 테이블에서 파생시킨다. 규칙이 여러 곳에
흩어지면 반드시 어긋난다.

## 10. 성공 지표

계산 정의는 [데이터 모델 9절](./data-model.md#9-파생-지표-계산-정의) 참조.

| 지표 | 정의 | 기준선 | 목표 (도입 6개월) |
|---|---|---|---|
| 시스템 경유율 | 신규 요구사항 중 FRMS로 접수된 비율 | 0% | 100% |
| 리드타임 중앙값 | 제출 → 완료 소요일 | 측정 불가(현행) | 우선 **측정 가능하게** 만들고, 3개월 데이터로 목표 설정 |
| 첫 검수 통과율 | 보완요청 0회로 완료된 건 비율 | 측정 불가 | 60% 이상 |
| 보완요청률 | 보완요청 1회 이상 발생한 완료 건 비율 | 측정 불가 | 40% 이하 |
| 기한 준수율 | 목표 완료일 내 완료된 건 비율 | 측정 불가 | 80% 이상 |
| 주간 활성 사용자 | 주 1회 이상 로그인한 사용자 수 | — | 대상 인원의 80% 이상 |
| 상태 정합성 | 실제 진행 상황과 시스템 상태가 일치하는 건 비율 (주간 회의에서 표본 점검) | — | 95% 이상 |

> 리드타임·통과율은 **현행 기준선이 없다**. 첫 목표는 개선이 아니라 **측정 가능하게
> 만드는 것**이다. Phase 2의 대시보드로 3개월치 데이터를 확보한 뒤 개선 목표를 설정한다.
