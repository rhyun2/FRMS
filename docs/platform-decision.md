## 1. 결정

> **FRMS는 자체 웹 애플리케이션 단독으로 구축한다.**
> MS Teams 기반 구현(네이티브 앱·봇·채널 알림)은 **MVP 범위에서 제외**하며,
> Teams 채널 알림 연동만 Phase 3의 선택 과제(`FR-804`)로 남긴다.

---

## 2. 맥락

- 조직 규모 약 20명, 기능 요구사항 월 20~50건.
- 현재 MS Teams와 SharePoint 리스트를 사용 중이며 Microsoft 365 / Entra ID 테넌트를 보유하고 있다.
- 따라서 "이미 Teams를 쓰는데 굳이 웹앱을 따로 만들어야 하는가"가 실제로 제기되는 질문이다.
  이 문서는 그 질문에 답하고, 나중에 같은 논의가 반복될 때 근거를 되짚을 수 있도록 남긴다.
- [PRD 2절](./PRD.md#2-배경-및-문제-정의)에서 정의한 문제(P1~P5)를 해결하는 것이 판단 기준이다.

---

## 3. 검토 대상

### 안 A — MS Teams 중심

Teams 채널을 작업 공간으로 삼고, SharePoint 리스트를 데이터 저장소로, Power Automate를
워크플로 엔진으로, Power Apps 또는 Teams 탭 앱을 입력·조회 화면으로 사용한다.
필요 시 Teams 앱 매니페스트를 등록해 채널 탭·봇으로 노출한다.

### 안 B — 자체 웹앱 중심

독립 웹 애플리케이션을 구축한다. Entra ID OIDC로 사내 계정 인증을 붙이고,
데이터는 자체 데이터베이스에 둔다. Teams는 사용하지 않는다(연동은 후순위 옵션).

> 참고: 검토 과정에서 "웹앱 + Teams 알림"의 하이브리드안도 논의했으나,
> MVP를 가볍게 유지하기 위해 **알림 연동 자체를 Phase 3으로 미루기로** 했다.
> 즉 안 B를 채택하되, Teams 연동은 나중에 붙일 수 있게 문을 열어둔다(7절).

## 4. 평가

가중치는 [PRD 3.1절 목표](./PRD.md#31-목표)에 대한 기여도로 부여했다.
점수는 5점 만점.

| # | 평가축 | 가중치 | 안 A (Teams) | 안 B (웹앱) | 판단 근거 |
|---|---|---|---|---|---|
| 1 | **진행단계 시각화 자유도** | 25% | 2 | 5 | 이 제품의 핵심 가치(G2). SharePoint 보드뷰는 선택 필드 기준 칸반까지는 되지만, 진행 스테퍼·회귀 마커·D-day 뱃지·보완요청 반복 표시 같은 커스텀 표현은 불가능하다. Power Apps로 만들면 가능하지만 그 시점에 이미 "앱을 만드는" 것이고, 웹앱보다 제약만 많다 |
| 2 | **전이 규칙·권한 강제** | 25% | 2 | 5 | [전이 매트릭스](./data-model.md#5-상태-전이-매트릭스)의 22개 전이를 "허용 역할 + 지정 담당자 본인 + 필수 입력값"까지 검증해야 한다. SharePoint 리스트는 항목 수준 권한과 폼 서식으로 일부만 흉내낼 수 있고, **리스트를 직접 열어 편집하면 우회된다**. 규칙이 우회 가능하면 규칙이 아니다 |
| 3 | **초기 구축 속도** | 15% | 5 | 2 | 안 A는 리스트 생성과 Power Automate 흐름 몇 개로 며칠 만에 형태가 나온다. 안 B는 최소 4~6주가 필요하다. 안 A의 유일한 명확한 우위 |
| 4 | **인증·계정 관리** | 5% | 5 | 4 | 안 A는 이미 로그인된 상태. 안 B도 Entra ID OIDC를 붙이면 실질적으로 동등하나 앱 등록 절차(오픈 이슈 O3)가 필요하다 |
| 5 | **알림 도달률** | 10% | 5 | 3 | 안 A는 사용자가 이미 보고 있는 곳에 알림이 뜬다. 안 B는 Phase 1에서 앱 내 알림만, Phase 2에서 이메일이 추가된다. **안 A의 실질적 우위이며, 안 B가 감수하는 대가** |
| 6 | **운영·유지보수 부담** | 10% | 3 | 3 | 안 A는 서버가 없지만 Power Automate 흐름이 늘어나면 디버깅이 어렵고 라이선스·커넥터 제약에 걸린다. 안 B는 서버·DB·백업을 직접 운영해야 한다. 20명 규모의 단일 컨테이너라면 부담은 비슷하다 |
| 7 | **확장성 (지표·리포트·연동)** | 5% | 2 | 5 | 단계별 체류시간, 회귀 원인 분포 같은 파생 지표는 SQL 한 번이면 되지만 SharePoint 리스트에서는 별도 추출·가공이 필요하다 |
| 8 | **종속성 (lock-in)** | 5% | 2 | 4 | 안 A는 데이터와 로직이 M365 테넌트에 묶인다. 안 B는 데이터가 자체 DB에 있어 이전이 자유롭다 |
| | **가중 합계** | 100% | **2.85** | **4.35** | |

## 5. 결정 근거

가중 점수 외에, 결정을 좌우한 판단은 다음 네 가지다.

1. **핵심 가치가 곧 커스텀 UI다.** 이 제품이 해결하려는 문제 P1("진행 상태가 보이지 않는다")의
   해법은 화면이다. 화면 표현력을 양보하는 선택은 제품의 존재 이유를 양보하는 것과 같다.

2. **우회 가능한 규칙은 규칙이 아니다.** 문제 P4("요건이 조용히 바뀐다")를 막으려면
   "승인 이후에는 요청 정보를 직접 수정할 수 없고 보완요청을 거쳐야 한다"는 제약이
   **강제**되어야 한다. SharePoint 리스트는 사용자가 리스트 뷰를 직접 열어 편집할 수
   있는 한 이 제약을 보장하지 못한다.

3. **Teams 네이티브의 실질 이득은 "알림 + 진입점"뿐이다.** 그 대가로 앱 매니페스트 작성,
   Entra 앱 등록, 테넌트 관리자 승인, Teams SDK 학습, Teams 안팎 두 벌 UI 대응을 치른다.
   MVP 단계에서 **두 플랫폼을 동시에 검증하면 검증 자체가 흐려진다.** 워크플로가 맞는지를
   먼저 확인하고, 알림 채널은 그 다음에 붙이는 편이 낫다.

4. **20명 규모에서 웹앱 운영 부담은 실제로 작다.** 앱 컨테이너 하나와 PostgreSQL 하나면
   충분하고(비기능 요구사항상 무중단 배포도, 수평 확장도 요구되지 않는다), 안 A가
   Power Automate 흐름을 관리하는 부담과 비교해 뚜렷이 무겁지 않다.

### 감수하는 것

이 결정은 **알림 도달률(평가축 5)을 명시적으로 포기**한다. Phase 1에서 사용자는
FRMS에 들어와야 자기 할 일을 안다. 이를 보완하기 위해:

- 랜딩 화면을 칸반 보드로, 로그인 직후 **내 할 일 큐**(`FR-503`)를 눈에 띄게 배치한다.
- 주간 진행 회의를 FRMS 보드 화면으로 진행하도록 운영 규칙화한다 ([PRD 리스크 R1](./PRD.md#11-리스크-및-완화)).
- Phase 2에서 이메일 알림(`FR-605`)과 지연 경고(`FR-606`)를 추가한다.
- 그래도 도달률이 문제로 남으면 Phase 3에서 Teams 알림(`FR-804`)을 붙인다 — 7절 경로 참조.

## 6. 이 결정을 재검토해야 하는 조건

아래 중 하나라도 **사실로 확인되면 안 A를 다시 검토**해야 한다.
결정 당시에는 모두 거짓이라고 전제했다.

| # | 조건 | 확인 방법 |
|---|---|---|
| C1 | 사외/사내 웹 애플리케이션 호스팅이 보안 정책상 불가능하다 | 오픈 이슈 O1에서 확인 (Phase 1 착수 전) |
| C2 | Entra ID 앱 등록 승인을 받을 수 없다 | 오픈 이슈 O3에서 확인 (Phase 1 착수 전) |
| C3 | Phase 1에 투입 가능한 개발 리소스가 0.5인 미만이다 | 오픈 이슈 O6에서 확인 (즉시) |
| C4 | 사용자가 업무 시간 대부분 Teams 밖으로 나오지 않아, 별도 웹앱 방문이 현실적으로 기대되지 않는다 | Phase 1 종료 시 주간 활성 사용자 지표로 확인 |

**C1~C3은 Phase 1 착수 전에 반드시 검증한다.** 뒤늦게 확인되면 이미 투입한 개발이
버려진다. C4는 Phase 1 이후 지표로 판정한다.

### 이후에 재평가할 트리거

- 사용자 100명 초과 또는 여러 사업부로 확대
- 프로젝트/제품 라인이 다중화되어 조직 계층이 필요해짐
- 외부 협력사가 직접 요구사항을 등록해야 함 (현재는 비목표 N5)

## 7. Teams 연동을 나중에 붙일 때의 최소 경로

지금 Teams를 쓰지 않기로 했다고 해서 **미래 옵션을 닫지는 않는다.** Phase 3에서
`FR-804`를 구현할 경우의 최소 경로를 기록해 둔다.

1. Teams 채널에 **Workflows(Power Automate) 기반 수신 커넥터**를 하나 만든다.
   (구 Office 365 Incoming Webhook은 단계적으로 폐지되고 있으므로 Workflows 방식을 쓴다.)
2. FRMS 백엔드는 이미 전이마다 알림 대상을 계산해 `notification` 레코드를 만든다(`FR-601`).
   그 발행 지점에 **HTTP POST 어댑터 하나를 추가**해 Adaptive Card를 전송한다.
3. 카드에는 FR 키·제목·전이 내용·담당자를 담고, 버튼은 **FRMS 상세 화면 딥링크**
   (`https://<frms-host>/fr/{fr_key}`) 하나만 둔다. 카드 안에서 상태를 바꾸게 만들지 않는다 —
   전이 필수 입력 검증(`FR-203`)을 카드에서 재현하려는 순간 규칙이 두 벌이 된다.

즉 필요한 것은 **어댑터 한 개**이며, 데이터 모델이나 워크플로를 바꾸지 않는다.
이 점이 안 B를 선택해도 손해가 크지 않은 이유이기도 하다.
